# Learning log

One line per step: what I learned, in my own words where possible.

- 2026-11-15, Step 0.1: monorepo scaffold. Turborepo runs tasks in package-dependency order and skips work whose input hash is unchanged; strict TypeScript plus `noUncheckedIndexedAccess` makes missing values a compile error. Note: `toolbridge-step-0.1-monorepo-scaffold.md`.
- 2026-11-16, Step 0.2: host domain and deterministic seed. A seed is repeatable only if every source of change is pinned: random numbers (seeded generator), time (fixed reference date) and ids (built from fixed inputs). Money as integer cents; order items keep a price snapshot. Note: `toolbridge-step-0.2-deterministic-seed-data.md`.
- 2026-11-16, Step 0.3a: read API, JWT auth and roles. Authentication (401: who are you?) and authorization (403: are you allowed?) are separate guards; protect every route by default and opt out with @Public(). Writing the role rule and its Swagger text from one value keeps docs honest for agents. Note: `toolbridge-step-0.3a-api-auth-and-docs.md`.
- 2026-11-16, Step 0.3b: safe writes. Read-check-write is a race; use a conditional atomic update (match only the allowed state, or check-and-increment a counter in one $expr update) and wrap multi-document changes plus their audit record in a transaction. Proved rollback with a half-failing order. Note: `toolbridge-step-0.3b-safe-writes.md`.
- 2026-11-17, Step 0.4: spec export and e2e tests. Treat the OpenAPI spec as a committed build artifact with a CI drift check; NestJS needs decorator metadata, which tsc emits and Vitest does not, so e2e tests run the compiled app with Supertest. Phase 0 complete. Notes: `toolbridge-step-0.4-spec-export-and-e2e.md`, `toolbridge-phase-0-summary.md`.
- 2026-11-17, Step 1.1: LLM port. Core code depends on our own `LLMProvider` interface; the OpenAI-compatible adapter only translates types, and a fake provider makes tests model-free. Streamed tool calls arrive in pieces keyed by `index` and must be accumulated (Ollama sends them whole, others split them). qwen3.5:4b runs ~10 tok/s, 56/44 CPU/GPU, about 9 s per turn. Context is set in a Modelfile because the OpenAI API cannot set it. Note: `toolbridge-step-1.1-llm-port.md`.
- 2026-11-17, Step 1.2: tools and executor. A tool is name + description + Zod schema (which becomes the JSON Schema the model sees and validates what it sends back) + safety class. The executor never throws: unknown tool, bad JSON, schema errors, 404/403/409 and timeouts all return as results the model can act on. Only read tools are retried (backoff with jitter); writes never are, because a retry after a timeout could refund twice. Hide internal ids from the model (`request_refund` takes the order number). Note: `toolbridge-step-1.2-tools-and-executor.md`.
- 2026-11-18, Step 1.3: agent loop and CLI. The ReAct loop is just: call model, run its tool calls, append results as `tool` messages, repeat until a text answer. Explicit stop conditions (answer, max iterations, consecutive tool errors, length) keep it bounded. Calls from one turn are independent, so reads run in parallel; writes run in order. Verified: a 3-call chain (get_order, then get_customer and list_orders in parallel), recovery from a 404, the iteration guard, and an honest "API unavailable" answer when the host was down. Note: `toolbridge-step-1.3-agent-loop.md`.
- 2026-11-18, Step 1.4a: streaming and structured logs. The loop streams every turn; text and Ollama thinking (`reasoning-delta`, display-only) print live. Pino writes JSON lines tagged with a per-run `runId` via `logger.child`, attached through the onEvent observer so the loop has no I/O. Seen live: the model asked for `limit: 100`, Zod rejected it (max 20), and its thinking said "the maximum allowed is 20, let me try again". Note: `toolbridge-step-1.4a-streaming-and-logs.md`.
- 2026-11-18, Step 1.4b: failure lab and context budget. Failures, then fixes:
  - Oversized result (59,122 chars, raw 100 orders) at 16K context: Ollama processed only 166 prompt tokens, silently dropping the whole tool message; the model said it had no order list. Fix: the executor caps every result at 8,000 chars with an explicit truncation note.
  - Truncation alone got the right order but a 10x wrong total ($51.39 vs $513.91): raw orders have many cent fields. Fix: list tools return shaped summaries (15,377 vs 59,122 chars for 100 orders); with shaping the answer was correct.
  - Paginated 50-order question with raw pages: too slow to finish (aborted). Fix: `hasMore`/`nextPage` hints; the model fetched exactly 3 pages with the prompt at 4.8K tokens. Still open: it added 50 numbers in its thinking for minutes and hit the 7-minute cap. Aggregates belong in tools, not in the model.
  - Context measured at 8K/16K/32K (5K-token prompt): 3.62/3.93/4.56 GB, 48/44/38% on GPU, ~900 prompt tok/s and ~11 output tok/s at all sizes. Context costs memory, not speed; changing it reloads the model (~11 s). Kept 16K (ADR 0011). Note: `toolbridge-step-1.4b-context-budget.md`.
- 2026-11-18, Gemini fallback experiment (ADR 0012): the unchanged OpenAI-compatible adapter got a correct tool call from gemini-3.5-flash with only config changes, which is ports and adapters paying off. But the follow-up turn failed: Gemini requires a hidden `thought_signature` echoed back, and our neutral `ToolCall` drops it. "OpenAI-compatible" is not identical. The free tier also had 503s and a 5/min, 20/day quota, and may train on inputs. Kept as a documented manual option only.
- 2026-11-18, Step 2.1: spec loader and intermediate model (ADR 0013). The parser read a local file through `$ref: "./secret.json"` by default (Local File Inclusion); `resolve.external: false` stops it, and a test keeps it stopped. Its `safeUrlResolver` refused a 127.0.0.1 URL with 0 requests reaching the server. `circular: 'ignore'` keeps every ref in a cycle, so cycle targets go into `ApiModel.schemas`. Host 41 ops / 0 warnings; GitHub 1,281 ops (14 MB, no security schemes declared); Stripe 612 ops (218 cyclic schemas, all bodies form-urlencoded, 273 GETs with bodies). Note: `toolbridge-step-2.1-spec-intermediate-model.md`.
- 2026-11-19, Step 2.2: tool generator (ADR 0014). Host spec + overrides file -> 35 tools (19 read, 16 write, 4 high risk, 3 merged lookups) in a golden snapshot. The generator exposed two host spec bugs a model would have tripped on: `page`/`limit`/`dryRun` typed `object` (no type annotation next to an initializer) and 15 ObjectId path params typed as an empty `Function` object; both fixed in the host. In @nestjs/swagger, `ApiParam({ schema })` merges with the guessed type, `ApiParam({ type })` replaces it. Route mentions ("GET /customers?search=") are rewritten to tool names. Tool menu: host ~5.6K tokens (a third of 16K), GitHub ~458K, Stripe ~380K, so Phase 3 retrieval is required. Note: `toolbridge-step-2.2-tool-generator.md`.
- 2026-11-19, Step 2.3a: HTTP executor for generated tools (ADR 0015). Generated tools returned byte-identical order and customer data to the hand-written ones, with the same 404/409/403/timeout/network failures; an expired token re-logs in once. SSRF: the address check runs inside the DNS lookup of the client's own connection pool, because an experiment showed keep-alive reuses sockets and skips a per-request lookup entirely. Refused: 127.0.0.1 (unless allowlisted), `localhost` (resolved to ::1), 169.254.169.254, [::1], and `..` path values. Unshaped `orders_list` is 2,190 chars vs 526 hand-shaped, which is 2.3b's job. Note: `toolbridge-step-2.3a-http-executor.md`.
- 2026-11-19, Step 2.3b: generic result shaping (ADR 0016). Field allowlists in the overrides file (checked against the response schema; a deliberate typo "statsu" was caught) plus automatic `hasMore`/`nextPage` on page responses. `orders_list` went from 2,190 to 582 chars. Found that truncation cut off the paging hint when it came after the items, so paging fields now come first and survive the 8,000-char cap. Agent runs with the 35 generated tools: chained order -> customer answer correct (~65 s), and "how many delivered orders" answered 382 from `total` (matches the API). But the model asked for limit 100 and the prompt jumped from 6.1K to 11K tokens; a per-tool limit cap is a follow-up. Note: `toolbridge-step-2.3b-result-shaping.md`.
- 2026-11-20, Step 2.4: content-addressed spec cache and breaking-change diff (ADR 0017). Measured first: on GitHub's 14 MB spec, validation is ~90% of the cost (about 1.3 s of 1.5 s), and yesterday's 16.5 s was the download. So the cache key (sha256 of canonical spec + overrides + COMPILER_VERSION) is computed after a cheap parse and before validation: 1,492 ms miss vs ~310 ms hit. A reformatted, key-reordered copy was still a hit; editing overrides was a miss; a corrupt cache file was a miss. The diff of the Step 2.1 host spec against today's flagged 24 operations as breaking (the Step 2.2 type fixes) with the version still 0.1.0: bug fixes can be contract breaks, and version labels cannot be trusted. Note: `toolbridge-step-2.4-content-addressed-cache.md`.
- 2026-11-20, Step 2.5: MCP server (ADR 0018). New package on the MCP TypeScript SDK v2 (it split into server/client/node packages); tools registered with `fromJsonSchema`, so the compiled schemas go out unchanged, and every call runs through the 2.3 executor. The official client check passed over stdio and Streamable HTTP. First run had 8 "failures" that were 403s: the server acts as one service account (support), and reports and coupons are owner-only. Permissions travel end to end; the check now tests both roles. MCP Inspector 2.10.1 (CLI mode, reading `.mcp.json`) listed 35 tools and called one; 2.11+ needs Node 24.22. Annotations are hints with cautious defaults, never security. Note: `toolbridge-step-2.5-mcp-server.md`.
- 2026-11-20, Step 2.6a: platform API, tenants, specs and tools (ADR 0019). Pool model with a `TenantScoped` repository that cannot exist without a tenant id and adds `tenantId` to every query; the tenant comes only from the API key. Proof the test is real: with the scope deliberately removed, the isolation test failed (Bob got 200 on Alice's spec instead of 404). API keys `tb_<keyId>_<secret>`, SHA-256 at rest, constant-time comparison, rotation and revoke (last key protected). Re-upload rules: new writes disabled, breaking writes needs_review, removed tools inactive. SSRF for spec URLs reuses the 2.3 client (lookup-time check, no redirects) with the allowlist only in platform config. 18 e2e + 17 unit tests. First failing e2e run was my own wrong assumption (no overrides gives 41 tools, not 35). Note: `toolbridge-step-2.6a-multi-tenancy.md`.
- 2026-11-20, Step 2.6b: tenant credentials with envelope encryption (ADR 0020). Each secret gets its own random data key and 12-byte IV (AES-256-GCM); the data key is wrapped by the master key with its version stored beside it; AAD binds both to tenant and connection. Connections are write-only; a tool call checks enabled/status first and only then decrypts. Proof the AAD test is real: with AAD made constant on purpose, Alice's ciphertext decrypted in Bob's record (200 instead of 500). Rotation tested end to end across three app starts (v1, v2 with v1 as previous plus re-wrap, v2 alone); ciphertexts unchanged. Against the real host: orders_get through an encrypted login worked, the host's role check still applied (owner-only report 403), and a disabled write tool was refused by the platform. Honest limit: a local master key protects against a database leak, not a compromised server. Note: `toolbridge-step-2.6b-envelope-encryption.md`.
- 2026-11-21, Step 3.1: tool index (ADR 0021). New `packages/retrieval`: an `EmbeddingProvider` port with an Ollama `/api/embed` adapter (`qwen3-embedding:0.6b`, 1024 dimensions, unit length, measured), a pure tool-text builder, a content-addressed embedding cache, and `tool_vectors` with an Atlas Vector Search index pre-filtered on tenantId and specId. `index:check`: 35 embedded from empty, 0 when unchanged, exactly 1 after editing one description, 0 (from cache) after reverting, 1 removed. The platform reindexes synchronously after each upload; a failure marks the index `stale` instead of failing the upload. Bug found by the e2e suite: right after a drop, Atlas Local still lists the old index as `DOES_NOT_EXIST`, and treating it as existing waited forever. Scores are tightly bunched (0.79 to 0.91), so 3.2 should not rely on a fixed threshold. Note: `toolbridge-step-3.1-tool-index-embeddings.md`.
